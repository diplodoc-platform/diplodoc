# Release Train

_[English version](README.md) · [Техническая спецификация](../../specs/release-train.md)_

**Release train** («поезд») сливает набор связанных pull request'ов в
репозиториях diplodoc и выпускает получившиеся пакеты в порядке зависимостей,
чтобы изменение, затрагивающее несколько пакетов, попало в npm целостным
набором.

Для каждого пакета поезд дожидается CI, сливает feature PR, дожидается
release-please PR и публикации в npm — и только после этого запускает пакеты,
которые от него зависят.

## Запуск поезда

Поезда запускаются вручную через workflow **Release Train** в этом репозитории
(`.github/workflows/release-train.yml`):

| Параметр | Значение |
| --- | --- |
| `prs` | Участники: `cli#123`, `owner/repo#123` или ссылки на PR, через запятую |
| `branch_name` | Запасной способ: все репозитории с открытым PR на этой ветке |
| `packages` | Ограничивает поиск по `branch_name` перечисленными репозиториями |
| `train_id` | Ключ для возобновления. При первом запуске оставьте пустым — станет `rt-<номер запуска>` |
| `concurrency` | Сколько пакетов обрабатывать одновременно (по умолчанию из `release-train.yml`) |
| `dry_run` | Построить план и таблицу, ничего не сливая |

Для каждого поезда создаётся **tracking issue** в `diplodoc-platform/diplodoc`
с заголовком `Release train: <train_id>`. Этот issue — одновременно живая
панель состояния и надёжное хранилище состояния: скрытый блок `RT-STATE` внизу
читается при возобновлении.

## Режимы

**Feature PRs** (по умолчанию) — участники это уже открытые вами PR. Передайте
их в параметре `prs` либо разместите на одной ветке и укажите `branch_name`.

**Dependency drift** (дрейф зависимостей) — аудит
(`.github/workflows/release-train-audit.yml`) сравнивает диапазоны
`@diplodoc/*` в каждом репозитории с опубликованными версиями и создаёт issue с
отставаниями. Комментарий `/rt start` в нём создаёт PR с обновлениями и
запускает поезд.

**Dry run** — строит план, таблицу и расписание, ничего не сливая.

## Команды в tracking issue

Участники настроенной команды GitHub могут писать в комментариях:

- `/rt resume` — перезапустить поезд с места остановки
- `/rt resume prs=cli#123` — возобновить и добавить участников
- `/rt start` — (в drift-issue) создать PR с обновлениями и запустить поезд

При возобновлении пакеты со статусом `done` и `released` пропускаются, упавшие
и заблокированные повторяются, а перед действиями поезд сверяется с
реальностью: уже слитый feature PR, слитый release PR или уже опубликованная
версия распознаются, а не выполняются заново и не считаются ошибкой.

## Как читать таблицу

| Колонка | Значение |
| --- | --- |
| `Repo` | Репозиторий пакета |
| `Feature PR` | Участвующий PR и признак готовности к мержу (ниже) |
| `Status` | Стадия пакета |
| `Release PR` | PR от release-please, появляется сразу после его создания |
| `npm` | Опубликованная версия или `1.2.3 (pending)`, пока npm не подтвердил |
| `CI` | Сводное состояние проверок feature PR (ниже) |
| `Snapshots` | Обновление снапшотов/скриншотов, запущенное поездом |
| `Duration` | Время с начала обработки пакета |

### Колонка CI

Одна ячейка агрегирует **все** проверки на последнем коммите feature PR:
несколько workflow (Quality на трёх ОС, покрытие, безопасность, lock-файл, а
также e2e и визуальные тесты отдельных репозиториев) сводятся в одно значение.
Проверки ботов и самого релизного механизма (`auto-approve`, `release-please`,
`publish`, `dependabot`, …) исключены — поезд ждёт не их.

- ✅ — все значимые проверки завершились успешно
- ⏳ `pending` — проверки ещё идут, упавших нет
- ❌ `[проверка](ссылка)` — проверка упала. Показывается **сразу, как только
  покраснела первая**, с пометкой `(N still running)`, если остальные ещё идут;
  не нужно ждать самую медленную задачу матрицы, чтобы увидеть падение
- ⏸ `re-approval required` — поезд обновил снапшоты, требуется повторное ревью
  и одобрение человеком

### Признак готовности к мержу

Рядом с feature PR: ✓ — все требования для слияния выполнены; ✗ — с указанием
причины (`review required`, `changes requested`, `conflicts`, `behind base`,
`blocked`). Это живое отражение состояния мержа в GitHub, поэтому отсутствие
аппрува видно задолго до того, как поезд дойдёт до пакета.

### Статусы

`queued` → `bumping` → `waiting_ci` → `merging` → `release_pending` →
`released` → `done`, а также:

- ⚠️ `needs human — 17m left` — мерж заблокирован (защита ветки, нет ревью).
  Поезд взводит auto-merge и ждёт до конца отсчёта; если PR успеет слиться,
  пакет продолжит движение. Настраивается через `merge_grace_min` /
  `merge_grace_poll_s`.
- ⛔ `blocked by <repo>` — упал пакет, от которого зависит этот. Независимые
  пакеты продолжают ехать.
- `waiting_release_review` — release PR требует ручного мержа, ожидание истекло.
- `failed` — причина в комментарии к issue, продолжить через `/rt resume`.

## Порядок зависимостей и параллельность

Порядок выпуска берётся из закоммиченного `deps-graph.json`. Поезд строит из
него собственный DAG: пакет стартует, когда опубликованы **все его зависимости
внутри этого поезда**, поэтому независимые пакеты едут параллельно.

`concurrency` (по умолчанию `3` в `release-train.yml`) ограничивает число
одновременных пакетов. Каждый пакет в работе стоит примерно 6–10 задач CI,
поэтому 3 загружают пул из 20 раннеров, не переполняя его. `concurrency: 1`
даёт строго последовательное поведение. Dry run печатает получившиеся «волны»
расписания.

## Обновление зависимостей

После публикации пакета версии нужны тем пакетам, которые в поезде идут дальше.
Поезд записывает это обновление в ветку пакета **один раз, прямо перед его
ходом**, одним коммитом со всеми накопленными версиями:

```
chore: bump @diplodoc deps for release train rt-11 (@diplodoc/utils@1.2.3, @diplodoc/client@5.11.2)

Release train: diplodoc-platform/diplodoc#106
```

Ссылка на issue связывает коммит с историей tracking issue. Один бамп на пакет
означает один перезапуск CI на пакет, а не перезапуск после каждого релиза
вышестоящего пакета.

Важное следствие: feature PR, слитый вручную **до своего хода**, обновления не
получит. Сливайте участников через поезд либо полагайтесь на последующий аудит
дрейфа.

## Долгие запуски

Поезд регулярно работает дольше часа — времени жизни installation-токена
GitHub App. Оркестратор перевыпускает токен сам (`app-token.js`) из
`RT_APP_ID` / `RT_APP_PRIVATE_KEY`: заранее до истечения и ещё раз, если вызов
отклонён. Поэтому длительные ожидания CI больше не заканчиваются ошибкой
`Bad credentials (HTTP 401)`.

## Конфигурация и разработка

- `release-train.yml` — список репозиториев, политика мержа и одобрения,
  таймауты, параллельность
- `deps-graph.json` — граф зависимостей и порядок выпуска
  (`npm run deps-graph`)
- `npm run test:scripts` — юнит-тесты этих скриптов

Локальный dry run:

```bash
GH_TOKEN=$(gh auth token) node scripts/release-train/prepare.js --prs cli#123 --dry-run --no-issue --output plan.json
```
